## 源码发现：已确认的结构与尚未证明的原因

车端运行驱动 SHA256：`d671e564242b9058d2ab4fc6fd7d2b64dfa5406c49618e1715fba176f77efce1`。驱动有写锁、单调时钟看门狗和反馈校验，但未记录所有 TX 帧及 ROS 命令来源。没有 ROS 命令时，仍每约 0.1 s 发零速、每 0.02 s 发 `0x09` 查询、每秒发电池及 `0x21` 主机信息。写锁保证 Python 单帧 write 不交叉，不保证 MCU 已处理完上一帧。

本地参考源码为 `底盘原理图及程序/EPRobot_controller_1.3-20210520`，**尚未证明与车上固件一致**：

1. `bottom_uart.c` 的中断回调和工作线程共享 `buffer/cmd`。校验后立即允许覆盖，下游使用时无帧副本，也会 memset 同一缓冲区；有覆盖、混用不同帧的风险。查询与主机信息的载荷位置和速度载荷位置重合。完整 TX 与 MCU 状态缺失，不能证明本次触发了这种竞态。
2. `bottom_pid.c` 左右电机的增量均可能被加两次；只有 `Error==0 && Set_speed==0` 才清 PWM/误差，目标零未必立刻意味着 PWM 零。可能放大错帧或测量噪声，但尚未作固件实证。
3. 通信计数由任何收到的命令重置，持续查询可保持通信活跃，不能把 ROS 没有行驶发布者等同于 MCU 没有输出。
4. `bottom_encode.h` 参考值为轮径 0.062 m、1560 脉冲/转、采样 20 ms、kv=1；代码旁还留有不同实际脉冲数的注释。这是后续核对项，未据此修改标定。

上传 helper 的复制路径使用 scp，不自动执行目标文件。不过上传发生时旧底盘驱动仍在运行，所以单凭“复制不执行”不能排除实车运动。系统负载、串口帧时序、MCU竞态或其他瞬时来源均需证据，不能归因于某一种。
